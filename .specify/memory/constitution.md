# FreshLine Constitution

## Core Principles

### I. Складская истинность
Каждая партия имеет свой срок и остаток. Приёмка, списание и движение фиксируются атомарно. Отрицательные остатки, расход просрочки и двойное списание запрещены.

### II. Контракт до параллельной реализации
OpenAPI, схема, инварианты и ADR публикуются до разделения веток. Изменение контракта сопровождается примером, миграцией (если нужна) и проверкой совместимости. Владельцы файлов указаны в `docs/TEAM_WORKFLOW.md`.

### III. Проверяемая вертикаль
Каждый P0-сценарий проверяется по цепочке браузер → Java API → PostgreSQL. Mock помогает разработке, но не доказывает готовность. DONE требует опубликованного SHA, проверок и воспроизводимого сценария.

### IV. Контекст в Git
После каждого малого проверяемого шага агент коммитит, пушит и обновляет `docs/progress`. Новый ноутбук начинает только от подтверждённого удалённого SHA. Никакого force push, `reset --hard` или параллельной записи в одну очередь.

### V. Честная и безопасная сдача
Демо содержит только синтетические данные. Секреты вне Git. Рабочий URL, QA PASS и готовность к показу утверждаются только после фактической проверки. Неисполненные проверки отмечаются NOT RUN.

## Технологические ограничения

Вся бизнес-логика backend — Java; PostgreSQL — единственный источник истины; интерфейс — React/TypeScript в браузере. Симулятор — отдельный контейнер без бизнес-правил. Дополнительные сервисы требуют ADR и доказанной необходимости. MVP не зависит от платных API.

## Рабочий процесс

Задачи выполняются по `specs/001-restaurant-inventory/tasks.md`; роли и ветки — по `docs/TEAM_WORKFLOW.md`. Интеграция минимум дважды в день. QA начинает матрицу до появления кода. Для merge проверяются контракт, миграции, релевантные тесты и отсутствие секретов. Релиз требует конкуренции заказов, повторов, границ срока, restart, cold start и ручного браузерного smoke.

## Governance

Изменение инвариантов или P0 записывается в `docs/DECISIONS.md` и отражается в спецификации и тестах. SemVer конституции: major — изменение принципа, minor — новый принцип, patch — уточнение. Тимлид принимает изменения продуктового правила. Прямые инструкции пользователя имеют приоритет.
