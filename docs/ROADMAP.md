## Точный порядок запуска полос

1. **Lead начинает первым:** T001 scaffold и T005 контракт/правила единиц, дат, ошибок, idempotency. Публикует SHA freeze и точки расширения Java ports. Одновременно Web делает T002/T007 по существующему OpenAPI, QA — T004/T008 по spec/contract. Никакой из этих потоков не ждёт готового backend.
2. **Data и Orders стыкуются через один порт:** Data может начать V1 по утверждённой модели; после G0 они фиксируют сигнатуры T014 **до** repository-кода T015/T018. Data берёт T003/T012/T015; Orders — T011/T017. Lead принимает ранний PR с V1 и domain ports; после него первым связывает delivery→PG→stock, не ждёт аналитики.
3. **После поставки — заказ:** Orders завершает T025/T027, Data — T026/locking, Lead — T028/T029. Web соединяет формы T020/T023/T030 с API, QA прогоняет QA-01…09. Первый G1 проверяется на реальном PostgreSQL, включая повтор запроса и гонку, прежде чем команда называет заказ готовым.
4. **После заказа — стоп-лист и рекомендации:** Data даёт availability/replenishment/offer SQL; Orders — risk/offer policy; Lead публикует GET endpoints. Web подключает stop-list/offers; QA сверяет причину и изменения после события. Математика рекомендаций остаётся объяснимой, прогноз ML не заявляется.
5. **Демо и выпуск:** Web создаёт отдельный HTTP simulator, Lead — SSE/Compose, Data — seed, QA — судейский путь. Затем Lead деплоит на VDS; Data проверяет backup/restore; QA повторяет сценарий на внешнем HTTPS; только затем Lead пишет фактический URL/SHA/tag в README.

**Критический путь:** G0 contract/ports → V1 миграция + policies → delivery/stock → atomic order/FEFO → stop-list → G1 реальный smoke → offers/demo → G2 → VDS/QA → G3. UI shell, QA-кейсы, seed-проектирование и подготовка сервера идут параллельно. Владелец следующего шага и входная зависимость для каждой задачи указаны в [планах ролей](lanes/lead.md) и [tasks.md](../specs/001-restaurant-inventory/tasks.md).

## P0 release gate

`tasks.md` T001–61, но приоритет определяется инвариантом, а не равномерным выполнением номеров. Обязательно: две партии с разными сроками, receipt/expiry, атомарный multi-dish order, FEFO, idempotency, стоп-лист, procurement advice, hot offers, отдельный demo client, веб-дизайн, HTTPS, тест конкуренции и понятный README. SSE делает демо живым; при сбое допускается polling с явным снижением статуса G2 и без фиктивного PASS. Нельзя сдавать отрицательные остатки или двойное списание как «известное ограничение».

## Правило при нехватке времени

Остановить необязательные эффекты и polish, стабилизировать вертикаль; честно отразить неполный критерий в README/QA. Не переносить P0 в список ★ без решения тимлида. Лучше законченный и проверяемый сценарий, чем недостоверное заявление о полном продукте.
