# Правила предметной области

Версия 1, 12.10.2026. Эти правила — решение команды там, где презентация не задаёт точный алгоритм. Их можно менять только через ADR + контракт + тесты.

## Количество и срок

- У ингредиента одна базовая единица: `g`, `ml` или `pcs`. Все рецепты/поставки/движения используют её. `NUMERIC(18,3)`, округление/float не допускаются; `pcs` целое.
- Партия связана ровно с одной строкой поставки. Положительное исходное количество, остаток от 0 до исходного.
- При `expiry_source=calculated` обязательны `manufactured_on` и `shelf_life_days ≥ 1`; `expires_on = manufactured_on + shelf_life_days - 1 день`. При `supplier_label` обязательна `supplier_expires_on`, она становится `expires_on`; оба способа и исходные поля сохраняются.
- Партия пригодна на дату `today` ресторана, если `expires_on >= today` и `remaining_qty > 0`. Сегодняшний последний день пригоден. При отсутствии даты поставка отклоняется.
- `days_remaining = expires_on - today` в календарных днях. `expired < 0`, `expiring = 0..warning_days` (по умолчанию 3), `fresh > warning_days`. Время UTC, календарь ресторана настраивается (`Europe/Moscow` для demo).
- Уведомление не меняет статус партии; изменение календаря и команда заставляют перечитать состояние. Запрещено расходовать просрочку даже если устаревший браузер показал её.

## Заказ и конкуренция

1. Валидировать непустой заказ, версии рецептов, положительное число порций и единицы. Снять snapshot версии рецепта в `order_item`.
2. Агрегировать потребность по ингредиенту across всех строк, включая повтор одного блюда.
3. В одной DB-транзакции получить idempotency row/claim по `(scope,key)` и сравнить canonical request hash. Для одинакового запроса вернуть прежний сохранённый HTTP результат, включая отказ. Для иного тела — 409 без изменений.
4. Блокировать строки ингредиентов по возрастающему UUID, затем все пригодные партии по `(expires_on,id)`. Под блокировкой на фиксированный `today` повторить расчёт. Не использовать браузерный предварительный расчёт для решения.
5. Если чего-то не хватает, сохранить `rejected` заказ, shortage и идемпотентный ответ; ноль consumption/negative movements.
6. Если хватает, распределить потребность FEFO; в той же транзакции обновить `remaining_qty`, добавить `consumption`, отрицательные `stock_movement`, accepted order, response и outbox. `CHECK remaining_qty>=0` страхует ошибку приложения.
7. Для приёмки положительное движение, партия, поставка, ответ и outbox — одна транзакция. Уникальность `(supplier, delivery_number)` не заменяет idempotency key.
8. Два одновременно поступивших одинаковых ключа сериализуются уникальным индексом/строкой. При lock timeout/deadlock bounded retry всей команды с тем же ключом. Команда не считается успешной до commit.

Инвариант `remaining_qty = SUM(stock_movement.delta)` для каждой партии: receipt +Q, consumption -Q, разрешённая ручная корректировка отдельным подписанным movement. В P0 ручной корректировки UI нет. Проверка инварианта — тест и диагностика, не фоновое исправление без аудита.

## Доступность, закупка, горячие предложения

- `available(ingredient) = sum(remaining_qty)` только пригодных партий. `possible_servings(dish) = min floor(available_i / recipe_qty_i)` по ингредиентам актуальной версии. В стоп-листе `possible_servings < 1`; причина — каждый ingredient с `missing = max(0, qty_i - available_i)`.
- Совет о закупке: если ≥7 дней истории, `daily_use = consumption_7d / 7`; `target = max(reorder_point, daily_use * cover_days)` (`cover_days=3` demo); `suggested = max(0,target - available)`. Если истории нет, использовать `reorder_point` и явно вывести `basis=insufficient_history`. Это правило, не ML-прогноз.
- Hot offers: считать только блюда с `possible_servings ≥1`. Для каждой пригодной партии, которая будет затронута при приготовлении одной порции по FEFO, `urgency = (warning_days+1-days_remaining)/(warning_days+1)` с ограничением в [0,1]; вклад `urgency * min(1,used_from_batch / remaining_qty) * (used_for_ingredient / recipe_qty_i)`. Score = сумма вкладов по ингредиентам, округленная лишь при выводе. Tie-break: меньший ближайший срок, затем dish ID. Выводить до 3 конкретных причин: продукт, дата, используемое количество. Golden fixtures фиксируют порядок. При нулевом сроке сегодняшняя партия имеет максимальный urgency.
- Score не заменяет ограничения доступности. После любой команды и в 00:00 локального времени витрины инвалидируются; первоначально SQL read-on-demand, без рискованного кэша.

## История и безопасность

Подтверждённые receipt/consumption/movement append-only. В публичном demo только синтетические данные; запись после demo access code, HTTPS, server session и CSRF. Production не запускается с demo seed/code. Симулятор использует те же endpoints и ключи, что браузер, и не пишет прямо в БД. Каждому запросу присваивается request ID; секреты/код доступа не логируются.
