# Работа Quantum404 на нескольких компьютерах

**Цель:** разработчик даёт агенту URL репозитория и один промпт; агент сам читает план, пишет код, тестирует, коммитит и пушит. Человек участвует только там, где требуется его аккаунт, сервер или продуктовое решение. Git хранит код и контекст, не историю чата, секреты или Docker volumes.

## Роли, ветки, файловые границы

| Участник | Ветка/полоса | Файлы | Начало |
|---|---|---|---|
| Lead (тимлид, backend, направление frontend) | `codex/lead` | `backend/app/` REST/security/events, root Compose/CI/deploy, контракт и интеграция | G0 |
| Backend orders | `codex/orders` | `backend/domain/`, FEFO, транзакционные use cases вместе с lead через PR; progress/orders | после G0 |
| Backend fullstack | `codex/web` | `frontend/`, `simulator/`, UX; согласованные API-подключения; progress/web | сразу с mock contract |
| Data engineer | `codex/data` | `backend/persistence/`, Flyway, SQL, индексы, dataset, backup; progress/data | сразу после G0 |
| QA | `codex/qa` | `qa/`, прогресс QA, defects/evidence без секретов; не переписывает доменные правила | сразу |

Три backend-разработчика — lead, orders, fullstack; один из них владеет frontend при лидерстве тимлида. DE остаётся самостоятельной полосой внутри Java-приложения. На одном и том же файле одновременно работает только владелец. HTTP-контракт и модель данных публикуются через G0; сигнатуры Java ports согласуются T014 до зависимых реализаций, затем изменение через PR + ADR. Два ноутбука, попеременно продолжая **одну** полосу backend, используют её общую удалённую ветку и lock в соответствующем `docs/progress/*.md`; другие полосы работают параллельно. Если людей больше, каждый работает в своей ветке, не ждёт переключения чужого ноутбука.

## Источник истины и цикл

Первый клон для участника: `git clone https://github.com/atomhuck/quantum404-freshline.git`, затем `git fetch origin`. Если его ветки ещё нет, `git switch -c codex/<lane> origin/main` и `git push -u origin codex/<lane>`; если есть — `git switch --track origin/codex/<lane>` либо обычный `git switch codex/<lane>` для уже локальной. Перед кодом всегда `git pull --ff-only`. На Windows лучше клонировать в обычную локальную папку вне OneDrive: файловая синхронизация и Git могут конфликтовать.

1. Агент читает `AGENTS.md`, свой план в `docs/lanes/`, `tasks.md`, текущий progress, последний `docs/handoffs/<lane>.md`, remote/branch/log/status. `DONE` без опубликованного SHA и проверок не считается.
2. На свободной полосе агент делает claim в progress (`FREE→ACTIVE`, owner, session UUID, task, UTC heartbeat), отдельный маленький commit и **обычный push до кода**. Одновременный claim одного remote head: только один push пройдёт; проигравший перечитывает статус.
3. Задачу делить на минимальные проверяемые результаты (обычно 5–20 минут работы агента): файл/миграция/endpoint/отрицательная проверка. После каждого результата: релевантная проверка → `git add <точные пути>` → diff + secret check → code commit `feat(T019): ...` → status commit с `last_verified_code_commit`, test command/result, next_step → push. Не ждать лимита аккаунта.
4. Перед каждым push `fetch`, проверить remote owner/session. Если другой владелец захватил ветку — не force/rebase поверх него; сохранить свой WIP в отдельной recovery-ветке, сообщить о конфликте.
5. Интегратор дважды в день (ориентиры 12:00 и 20:00 МСК) делает PR/Merge в `codex/integration` от актуальной `main`; каждый PR запускает contract/build/test. После проверенного merge обновляет снимок прогресса и gate в `README.md`. Результат интеграции может исправляться в полосе владельца; UI никогда не заменяет серверные правила.
6. `main` обновляется после реального вертикального smoke; перед сдачей tag `submission-2026-10-17` фиксирует полный SHA. Требуемое GitHub review не назначать так, чтобы оно создало человеческий блокер; автоматические checks обязательны.

## Форма `docs/progress/<lane>.md`

В начале файла YAML front matter: `state` (`FREE|ACTIVE|HANDOFF|INTERRUPTED`), `owner`, `session_id`, `branch`, `current_task`, `substep`, `last_verified_code_commit`, `checkpoint` (`VERIFIED|WIP|NOT_RUN`), `next_step`, `heartbeat_utc`, `human_required`. Далее: таблица DONE/WIP/TODO task IDs, фактические команды/выходы, известные ошибки, зависимость от чужого PR, точный следующий файл/действие. SHA статус-коммита не записывать в него самого. Секреты только по имени переменной.

`progress` — текущее состояние. [Журналы `docs/handoffs/`](handoffs/README.md) — неизменяемая хронология плановых передач и takeover; новая запись сверху, прежние не переписывать. [Планы `docs/lanes/`](lanes/lead.md) — последовательность и критерии работы. README показывает быстрый снимок по ролям; при расхождении полоса сверяется с её remote HEAD, progress и журналом.

## Плановая передача A → B

1. Закончить малый шаг или честно пометить WIP. Если запущен simulator/dev-consumer, остановить дубликат; общий production-сервер не выключать без нужды.
2. Зафиксировать код и тесты. В одном status-коммите обновить `docs/progress/<lane>.md` (`HANDOFF`, задача, последний проверенный code SHA, ошибки, запуск, next_step) и добавить реальную запись в `docs/handoffs/<lane>.md` по [форме](handoffs/README.md). Указать только **имена** секретов. Push.
3. Сверить `git ls-remote origin refs/heads/<branch>` с опубликованным локальным HEAD. Сообщить человеку только ветку/SHA и факт готовности передачи.
4. B клонирует/открывает репозиторий, вставляет `prompts/<role>.md` в новом чате. Агент fetch, `pull --ff-only`, читает **последнюю запись журнала и progress**, проверяет status и claim-ит полосу. Если HEAD не совпал, не продолжает на догадке.

## Внезапное прерывание и takeover

| Состояние | Восстановление |
|---|---|
| Код и status в remote | Новый ноутбук подтверждает, что старый агент остановлен, делает claim, продолжает next_step |
| Код запушен, status старый | Сравнить commits с recorded SHA, прогнать тесты, восстановить status только из фактов |
| Commit только на старом ноутбуке | До push второй видит только старый remote; при доступе к первому опубликовать commit, иначе начать с remote |
| Незакоммиченные изменения | При доступе сохранить WIP после проверки секретов, push; без доступа они не переносимы |
| ACTIVE у другого, старый heartbeat | Таймер не даёт права самозахвата. Человек сообщает «прошлый агент остановлен» либо старый публикует HANDOFF |
| Push отклонён non-fast-forward | Fetch и проверить owner. Не force push; чужой claim имеет приоритет |
| Merge/rebase не закончен | Прочитать `git status`, сохранить изменения, разрешить по контракту; не запускать reset |
| DB/volume на другом ПК | Восстановить synthetic seed или проверенный приватный backup; Git не переносит данные |

Единственное обязательное человеческое подтверждение аварийного takeover предотвращает двух активных владельцев и потерю работы. При плановой передаче достаточно HANDOFF-коммита, повторной просьбы о разрешении нет.

## Завершение и доказательства

Для каждого task ID: код/документ, тест на релевантном уровне, commit SHA, push, progress. Для API/schema: обновлены OpenAPI/пример/миграция и интеграционный тест. Для UI: screenshot desktop + mobile, клавиатура и ошибка. Для гонок: реальный PostgreSQL. Для релиза: внешняя HTTPS-проверка, резервная копия/restore и ручной QA. Зелёный mock не равен release.
